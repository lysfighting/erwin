# /erwin-init

Initialize the erwin cognitive framework for any project — new or existing.

This is NOT a project scaffolding tool. It installs a **cognitive operating system** that enables:
- Direction continuity across AI sessions (CURRENT.md + GOALS.md)
- Decision memory that survives context windows (ADRs)
- Self-evolving project understanding (MEMORY.md + session logs)
- Structured idea capture and incubation (Idea Garden)

**Hard boundary: this skill never touches code, never asks about tech stack, never generates project scaffolding.**

**Run from the project root directory.**

---

## Phase 1: Install Infrastructure (automatic, zero questions)

### Step 1: Detect Project Name

```bash
PROJECT_NAME=$(basename "$(pwd)")
```

No questions. The directory name IS the project name.

### Step 2: Safety Check

```bash
# Check if files already exist
[ -f CLAUDE.md ] && echo "WARNING: CLAUDE.md exists"
[ -d _project ] && echo "WARNING: _project/ exists"
```

If either exists, use `AskUserQuestion`:
- "CLAUDE.md / _project/ already exists. Overwrite?" → Yes (fresh init) / No (abort) / Merge (add missing files only)

### Step 3: Create Directories

```bash
mkdir -p _project/ideas/skills _project/ideas/meta
mkdir -p _project/decisions _project/sessions _project/issues _project/releases
mkdir -p .claude/rules
```

### Step 4: Write All Files

Use the `Write` tool for each file. Substitute `{project-name}` with the detected project name. Use today's date for `{date}`.

**Write in this order:**
1. All `_project/` README files (independent)
2. `_project/GOALS.md`, `_project/CURRENT.md`, `_project/ROADMAP.md`
3. `CLAUDE.md`
4. `.claude/rules/ai-workflow.md` and `.claude/rules/git-conventions.md`
5. `CHANGELOG.md`

Templates for each file are below.

### Step 5: Initialize Auto-Memory

```bash
# Compute Claude Code's project hash (path → hash)
PROJ_HASH=$(pwd | tr '/' '-')
mkdir -p ~/.claude/projects/$PROJ_HASH/memory/
```

Write `~/.claude/projects/$PROJ_HASH/memory/MEMORY.md` using the MEMORY.md template below.

### Step 6: Git Init + First Commit

```bash
# Init git if not already a repo
git rev-parse --git-dir 2>/dev/null || git init

# Stage project intelligence files
git add _project/ CLAUDE.md CHANGELOG.md .claude/

# First commit
git commit -m "chore: init erwin cognitive framework

Bootstrap _project/ structure, CLAUDE.md, .claude/rules/, CHANGELOG.md.
Generated by /erwin-init (erwin framework v2.0.0)."
```

### Step 7: Report Phase 1 Completion

Output:
```
Project initialized: {project-name}

Created:
  _project/          (GOALS, CURRENT, ROADMAP, ideas, decisions, sessions, issues, releases)
  CLAUDE.md          (AI navigation handbook)
  .claude/rules/     (ai-workflow.md, git-conventions.md)
  CHANGELOG.md       (Keep a Changelog format)
  ~/.claude/projects/{hash}/memory/MEMORY.md  (Claude's auto-memory)
```

## Phase 2: Project Understanding Conversation (prompted, skippable)

### Step 8: Offer GOALS.md Conversation

Use `AskUserQuestion`:

```
question: "Infrastructure is ready. Want to fill in GOALS.md now?"
header: "GOALS.md"
options:
  - label: "Yes — let's define the vision"
    description: "I'll guide you through articulating your project's purpose, success criteria, and boundaries. Takes 3-5 minutes."
  - label: "Not now — I'll do it later"
    description: "Skip to the end. You can fill in GOALS.md yourself anytime."
```

### If YES → Guided Conversation

Start a natural conversation to help the user articulate their project vision. Use `AskUserQuestion` for each dimension, but keep it conversational — not a form. The goal is to help the user think clearly, not to collect data.

**Dimension 1: Vision**

Use `AskUserQuestion`:
```
question: "In one sentence: what does {project-name} do, and for whom?"
header: "Vision"
options:
  - label: "I'll type it"
    description: "I have a clear picture — let me describe it."
  - label: "Help me figure it out"
    description: "I have a rough idea but need help articulating it. Let's talk through it."
  - label: "It's exploratory"
    description: "I don't have a clear vision yet — this is an experiment or learning project."
```

If "Help me figure it out" → ask follow-up questions naturally (who benefits? what problem? what changes?). Keep probing until the user can state their vision in one sentence.

If "It's exploratory" → write a placeholder vision acknowledging the exploratory nature. Don't force OKRs.

**Dimension 2: Success Criteria**

Use `AskUserQuestion`:
```
question: "How will you know {project-name} is succeeding? What's measurable?"
header: "Success"
options:
  - label: "I have concrete metrics"
    description: "I can define specific, measurable outcomes (users, performance, features)."
  - label: "Quality-based"
    description: "Success is more about quality — clean code, good UX, maintainability."
  - label: "Learning goals"
    description: "Success = I learned something. No production metrics needed."
  - label: "Skip this — too early"
    description: "I'll define success criteria once the project takes shape."
```

**Dimension 3: Anti-Goals**

Use `AskUserQuestion`:
```
question: "What is {project-name} explicitly NOT? What should Claude never suggest or build?"
header: "Anti-goals"
options:
  - label: "I have clear boundaries"
    description: "There are specific things this project will never do. Let me list them."
  - label: "Help me think about this"
    description: "I haven't thought about boundaries yet. Ask me some questions."
  - label: "No boundaries yet"
    description: "Too early to define anti-goals. Skip this."
```

If "Help me think about this" → ask probing questions: "Should it be simple or comprehensive? Fast or correct? For you or for others? Production or prototype?"

### Step 9: Write GOALS.md

Based on the conversation, write `_project/GOALS.md` with the user's actual answers — not template placeholders. Adapt the structure to what the user provided:
- If they gave full vision + OKRs → write complete GOALS.md
- If exploratory → write a lightweight GOALS.md with exploration framing
- If they skipped dimensions → leave those sections as templates

### Step 10: Infer Language Preference

Based on which language the user used during the Phase 2 conversation, update `~/.claude/projects/{hash}/memory/MEMORY.md`:

```markdown
## User Preferences

- **Communication language**: [inferred from conversation — e.g., "Chinese for discussion, English for code"]
```

If Phase 2 was skipped (user selected "Not now"), do NOT write any language preference — it will be discovered naturally in future sessions.

### Step 11: Commit GOALS.md Update

```bash
git add _project/GOALS.md
git commit -m "docs(project): fill in GOALS.md via /erwin-init onboarding"
```

### If NO → End

Output:
```
Done. The cognitive framework is installed.

Next steps:
  1. Fill in _project/GOALS.md when you're ready — your vision and success criteria
  2. Start working — Claude reads CLAUDE.md + CURRENT.md at the start of each session
  3. At session end, Claude will update CURRENT.md and write a session log automatically
```

```markdown
---
# AI session workflow rules
---

# AI Session Workflow Protocol

## When to Read CURRENT.md — Principle Over Checklist

**One test**: "If my next action goes in the wrong direction, how much work do I need to undo?"

- **High undo cost** → read `_project/CURRENT.md` first (30 seconds), then act
- **Low undo cost** → proceed directly

**Must read first** (action produces irreversible results):
- About to write code, create or modify files
- About to make architecture or technical decisions
- User says "continue", "next", "go", "drive"
- First substantive action after conversation starts

**No need to read** (pure conversation, no artifacts):
- Explaining concepts, answering technical questions
- Discussing approaches without committing to action

## Concurrent Reads (with CURRENT.md)

When reading CURRENT.md, also read:
- `_project/GOALS.md` — verify alignment with north star
- Relevant ADRs — if about to modify a component with decision records

## During Session

- Discovered bugs/tasks → create `_project/issues/ISS-NNNN-title.md`
- Major decisions → create `_project/decisions/NNNN-title.md`
- Good ideas → add to `_project/ideas/INBOX.md` immediately

## Session End (mandatory)

1. Update `_project/CURRENT.md`
2. Write `_project/sessions/YYYY-MM-DD.md`
3. Update `CHANGELOG.md` if features completed
4. Update `~/.claude/projects/{project-hash}/memory/MEMORY.md`
   — patterns, user preferences, technical gotchas, project-specific knowledge
5. Run: `git add -A && git commit -m "type(scope): description"`

## File Size Limits

| File | Target | Max |
|------|--------|-----|
| CLAUDE.md | <150 lines | 200 lines |
| _project/CURRENT.md | <80 lines | 120 lines |
| ADR files | 50-100 lines | 150 lines |
| Session logs | 50-150 lines | 300 lines |

## What Not To Do

- Don't skip CURRENT.md before irreversible actions — stale context = direction error
- Don't skip the session-end update — stale CURRENT.md = broken continuity
- Don't add large images or binary files to docs/ or _project/
```
