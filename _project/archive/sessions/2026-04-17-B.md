## A. Essence challenge

**但 n=1 不足以固化为 skill 形态**:

**Sprout 自身的 Risk #1 已承认**("Prematurely freezing the pattern at n=1")。Acceptance Criteria #1 也明确要求 n≥2 外加 (interrupt-recovery | cross-dependency | failed-checkpoint) 三选一。这份自觉是 Sprout 成熟的标志,但也意味着**现在不是 Plant 时刻**。

### A.2 独立价值 vs 吞进 tw2-drive/operations/team-execution.md?

核对 tw2-architecture.md:L75 / L139 — `team-execution.md` 当前定位是"**per-mission task-parallel**"(`/team-drive` 现有 team-mode 的 refactor target),不是 multi-mission fleet。

**结论**:语义确实正交。Sprout §Risks #2 也正确识别了这点。

**但结构摆放方式仍有挑战空间**:

- 方案 b(我的挑战): `/team-drive fleet` 或 `tw2-drive/operations/fleet.md` — 跟 team-execution.md 同属 drive 家族,一个是 intra-mission 一个是 cross-mission,**命名空间更统一**

### A.3 Mode-A first-checkpoint 是 fleet 独有纪律吗?

**自我更正**:初稿在这里有一处前提错误,保留此段以便审阅我如何改。

**n=1 两个 catch**:
- lead-1298 抓到 Contract 的函数名错误(`_allow_emission` 实际是 `_enabled`)
- lead-1302 抓到 Adjustment B 的 back-compat 陷阱

**核查:`/team-drive.md` 现状**:已经有 Anti-Compliance 纪律:
- L476 **"Anti-Compliance Core Rule"**:每个决策点 AGREE+EXTEND / CHALLENGE+PROPOSE / REDIRECT,never silent compliance(这其实是 Constitution P4)
- L480 "Proactive Triggers — challenge yourself during execution"
- L506 "**Sub-tasks are a suggested route (HOW) — challenge, revise, or confirm them**"
- L524 "Challenge each sub-task — ALL types (code + MANUAL)"

所以 **"push back on Contract errors" 这个 content 层面,/team-drive 已覆盖**。单 mission 用 `/team auto #N` 一条链走下来,driver 自己就负责 challenge —— 本来就不会丢。

**Mode-A 真正的独有机制**是 content 之外的 **form**:teammate **暂停,对外发送 SendMessage,等待 team-lead 批量回复后再进入 code**。这是 fleet 特有的:

- 单 mission 没有 team-lead,也没有"等待外部批复"的空间 —— challenge 由 driver 自我完成即可
- fleet 里 N 个 teammate 并行,team-lead 做**批量评审**,能一次看完 N 份 checkpoint 做横向对比(appendix 11:20 的 Option A 判决就用到了跨 mission 视角)

**修正后的 critique**(比初稿弱但更准确):

- ❌ 初稿说法:"Mode-A 的 challenge 纪律应上提到 /team-drive,fleet 只做 briefing templater"
- ✅ 修正说法:"Mode-A 的 challenge content 已经在 /team-drive 里了;Sprout 不应把它重新描述成 fleet 自有发明。Fleet 真正新增的是**external batch-review gate**——teammate 暂停 → SendMessage → team-lead 横向对比批复。这个 gate form 是 fleet 独有的合法价值。"

**Sprout 要补的是语言**:Notes §4 "Teammate challenge space must be explicitly protected" 目前读起来像 fleet 新发明的纪律;应改写为"fleet briefing 引用 `/team-drive.md:L476` Anti-Compliance 规则,并加 external-handoff-gate 规定"。这是 cite-existing 而不是 rename-existing。

**独立价值净评估**:fleet = orchestrator + external batch-review gate + briefing templater。比初稿"纯 orchestrator + briefing templater"强一档,但比原 Sprout 自述弱一档。A.4 继续讨论 orchestrator 本身够不够一个新 sub-command。

### A.4 `team-fleet` vs `team-swarm` / `team-parallel` / 融到 `/team auto`

Sprout §Naming-reserved 给出的理由:
- ✅ `team-swarm` 驳得好:竞品名空间冲突
- 🟡 `team-parallel` 驳为"generic":主观,且 generic 在语义准确时是优点
- 🟡 `team-missions` 驳为"sounds like dashboard":主观
- ❌ **没有考虑 `/team auto --missions #A,#B,#C`**:这是最显眼的 opposite test

`/team auto` 现在是 "end-to-end one-mission full automation"。表面上 `--missions #A #B #C` 像是对称扩展,但实测 team.md:3348-3394 的 Auto 状态机是 **围绕单一 Contract / 单一 worktree / 单一 driver** 设计的:A1 Select Issue → A2 Validate Issue → 后续 /team-drive + /team-ship 都是 single-lane。加 `--missions` 不是简单 flag 扩展,是整个状态机重构。

**修正后的挑战**(比初稿弱但更诚实):Sprout 的 naming 讨论漏了一个更根本的问题 —— **为什么新建一整层 orchestration,而不是把 `/team auto` 的状态机改成支持多 Contract**?两者都是"新增代码"量级,但后者命名空间更紧凑(Constitution P10 "6 skills, clear boundaries" 守护)。Sprout 应至少正面驳一次这个选项。

**注意**:我没有实证评估"扩展 /team auto"和"新建 /team fleet"哪个 engineering 成本更小。这是 Plant ADR 应做的 spike,不是 Sprout 阶段结论。

## B. Fit check against erwin

### B.1 GOALS 对齐度

**结论**:GOALS + CURRENT 足以说明 teamwork 不在 erwin 当前聚焦。"Legacy" 是优先级描述,**不是"禁止扩展"**。team-fleet 作为 erwin 的 Sprout → Plant → Fruit 路径,**等于用 erwin 的 attention budget 把 teamwork 从 legacy 重新 activate**。

这个成本不是零。投入 team-fleet 的时间不能同时投入:
- Radar 观察窗口(GOALS O1,已 100% 的 KR 实际是起点,不是终点)
- Harness 深化(CURRENT 显示 Phase 7 post-1.0 expansion 正在做)

**替代 framing(不是结论,是 lys 应明确做的 policy choice)**:team-fleet 的 n=1 经验**可能**更适合先进 `docs/knowledge/` 或 `docs/research/` 作为 durable pattern note 被 erwin 吸收,skill 层是否孵化是**独立 policy 决策**:

- 如果 lys 对"teamwork 冻结范围包括 fleet"答 YES → 不孵化 skill,pattern 进 knowledge 层即可
- 如果答 NO(teamwork 是 legacy 但 fleet 是能力缺口填补,可以破冻结)→ Sprout→Plant→Fruit 路径合理,Gap 1-9 补齐后重评

我的 review 只能从证据层说"n=1 不足以支持 Plant",不能替 lys 决定"fleet 是否破 teamwork 冻结"。后者是 policy,不是 evidence。

⚠️ **bias 披露**:初稿在此处写"Radar/Knowledge 路线更契合 GOALS",隐含了"teamwork 冻结范围包括 fleet"的 policy 判断。我没有权限做这个判断,所以改成二分路径让 lys 选。MEMORY 里的"6 skill limit + teamwork legacy"可能放大了我对新 sub-command 的抵触,bias scout 已标记。

### Popper(证伪主义,`06_20世纪上半叶.md:724`)

⚠️ 第 5 版自校(pantheon-verifier scout 指出):初稿只是把"可验证"换词为"强可证伪",**没 run Popper 方法核心**(bold conjecture + specific refutation signals)。补:

真正的 Popper 应用是**事前 enumerate**"什么 observation 会 falsify 这个 AC"。不是给 AC 分级强度,是给每条 AC 写死 specific falsification signals。

|---|---|
| Notes§1 isolation:"worktree" 冲突是 load-bearing | n=2 run 漏掉 `--unset-upstream` 步骤仍 ship 成功 |
