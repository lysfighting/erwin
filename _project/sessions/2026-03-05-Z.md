### 2. Branch Protection 讨论

vi_agent 提交并 push 后，**用户问**：`push,但是是不是 main 已经受到保护了?` — 我检查后发现 main 没有任何保护，直接推成功了。这个问题触发了整个 protection 讨论。

**用户之前说过**：`ci 还不稳定,不做强制要求,1 人 review 默认自己就行`

**问题**：GitHub 的 `required_approving_review_count: 1` 不允许 PR 作者 approve 自己。

**我提出两个方案**：
1. 不设 branch protection（现状，任何人可以直推 main）
2. 设 protection，require PR 但 review=0（必须走 PR，但不强制别人 review）

**用户问**：2 更好对吗?

**我的分析**：方案 2 严格优于方案 1，理由：
- 堵住直推 main + force push 的风险
- **保证 post-merge workflow 触发**（直推不触发 `pull_request` 事件，workflow 形同虚设）
- PR 是天然的 code review 记录
- 成本几乎为零（团队已经用 PR 流程，/team-ship 自动化了开 PR）
- 紧急 hotfix admin 可以 bypass

**用户确认**：设置方案 2。

**方案 1 vs 2 完整对比**（我给出的分析）：

| 维度 | 方案 1: 不设保护 | 方案 2: require PR, review=0 |
|------|---|---|
| 直接 push main | ✅ 可以 | ❌ 必须走 PR |
| force push main | ⚠️ 任何人可以 | ❌ 被阻止 |
| 一个人完成全流程 | ✅ | ✅ 自己开 PR 自己 merge |
| CI 必须通过 | N/A | ❌ 不强制 |
| post-merge workflow 触发 | 只在 PR merge 时 | **保证触发**（必须走 PR） |
| 误操作风险 | 高 | 低 — PR 是缓冲层 |
| 团队可见性 | 低 — push 无记录 | 高 — 每次改动有 PR 记录 |
| 紧急 hotfix | 直推 | admin 可 bypass |

**实际应用**：设置后 push 时 GitHub 返回 bypass 提示 — 说明 admin 可以绕过保护直推，非 admin 成员必须走 PR。

**用户说**：`设置,但是应该是 team skill 本身该做的事儿吧` — 指出这应该是 skill init 自动处理的，不是手动一次性修复。这句话直接驱动了下面的发现。

**额外发现**：team.md Step 5c 的 branch protection 逻辑是**硬编码**的 — `required_approving_review_count: 1` + `required_status_checks: ["quality"]`，完全忽略 `review_required` 和 `ci` 配置。

**修复**：Step 5c 改为根据 `quality.ci` 和 `quality.review_required` 动态生成规则。额外增加了原版没有的 `allow_force_pushes: false` 和 `allow_deletions: false`（防 force push + 防删分支）：

| `quality.ci` | `quality.review_required` | Protection 规则 |
|---|---|---|
| true | true | CI 必须通过 + 1 reviewer |
| true | false | CI 必须通过 + 只需 PR（无 reviewer） |
| false | true | 无 CI + 1 reviewer |
| false | false | 无 CI + 只需 PR（挡住直推 + force push） |

### 3. 分支模型问题（关键讨论）

**用户问**：`现在的设计是怎么管理分支?有多少分支?对应什么环境和流程?哪些 action?是不是少了 CICD`

**我的回答 — 现状**：

分支模型：单分支，只有 main + feature branches。vi_agent 实际有 ~20 个远程分支，至少 5 种命名模式（`feat/`、`feature/`、`features/`、`fix/`、`infra/`、`mission/`、个人 dev 分支如 `qianhua-dev`），命名不统一。

Workflows（仅 2 个，都是 CI 不是 CD）：

| Workflow | 触发条件 | 做什么 |
|----------|----------|--------|
| `ci.yml` | PR to main / push to main | 4 个服务 lint + test + build |
| `post-merge.yml` | PR merged | auto-label done + checkbox + milestone 通知 |

环境现状（config 定义了 `lifecycle: [dev, qa, released]` 但自动化不存在）：

| 环境 | 机器 | 现状 |
|------|------|------|
| dev | vi-agent 当前机器 | ✅ 有（手动部署，多租户端口隔离） |
| staging | 独立 GCP（规划） | ❌ 没有机器也没有 workflow |
| production | 独立 GCP（规划） | ❌ 没有机器也没有 workflow |

**CD 完全缺失** — 代码合入 main 后流程就断了：

```
Issue → Claim → Branch → Code → PR → CI → Merge → post-merge cleanup
                                                    ↓
                                              （到这里就断了）
                                           ❌ 没有自动部署到任何环境
                                           ❌ 没有 deploy workflow
                                           ❌ deploy.staging_workflow 引用了但不存在
```

**用户追问**：`每次新开发从prod tag 开始?然后 fix 就没那些要求对吗?也就是说未经验证通过的代码也在 main 分支对不对? 比如合并 feat 或者 fix 等之后 main 打了staging,还是有 bug`

**这是核心洞察** — 用户指出单分支模型的根本缺陷：

```
feat/A → main ✅
feat/B → main ✅（B 有 bug，但 CI 没发现）
fix/C  → main ✅
     ↓
main = A + B + C（全部未经 staging 验证）
     ↓
部署 staging → 发现 B 有 bug
     ↓
fix/B-hotfix → main（但 main 又多了 feat/D、E...）
     ↓
再部署 staging → 带进去 D、E 的未验证代码
     ↓
永远追不上，staging 永远不干净
```

**我的回答**：这不是 CI/CD 的问题，是分支模型的问题。解法是 release branch — 在准备发版时从 main 切出来，隔离验证。teamwork skill v2.6.0 其实已经设计了 `conventions.release_branch` 双分支模型，但 vi_agent 从未启用（release_branch 未配置，默认等于 base_branch，退化为单分支）。

**我问**：`要讨论怎么给 vi_agent 配起来吗？还是你觉得现阶段 V0.1 团队规模还不需要这么重？` — 给了用户 defer 的选项。

```
   hotfix PR → merge to release/V0.1（不碰 main）

4. 发版 ← ⚠️ 只有打 tag 的部分
   tag V0.1 → deploy prod
   release/V0.1 → merge 回 main
   删除 release/V0.1

5. 下个版本 → main 继续
```

### 5. Issue 版本追踪需求

**用户追问**：`是不是 issue 本身 label 等没有带 git tag 信息? 就是这个 bug 是啥版本的, 或者这个需求请愿是哪个版本的有吗? 有这套机制吗? 这个要求合理吗? 常见吗?`

**回答**：
- **Milestone** = 目标版本（Fix Version，要在哪个版本修）→ ✅ 有
- **Found-in version**（bug 在哪个版本发现）→ ❌ 没有
- **Affects version**（影响哪些版本）→ ❌ 没有
- config 里 `version:` label prefix 定义了但 **skill 从来没用过**

**这非常合理，是标准做法。** Jira 原生支持 Affects Version / Fix Version 两个字段。GitHub 替代方案是 `found-in:V0.1` label + Issue template 版本字段。

**当前 skill 缺口**：
1. `/team-issue` 不问也不设 found-in 版本
2. `setup-github-labels.sh` 不创建 `version:V0.1` 标签
3. Issue template 没有版本字段
4. 没有机制在 release 时回溯 "这个版本还有哪些已知 bug"

## 需求汇总（记录供未来 session 实现，本 session 不动手）

### A. Release 分支完整生命周期

1. **`/team-release prep {version}`** — 从 main 创建 `release/{version}` 分支，冻结范围
2. **Hotfix 路由** — bugfix PR target release 分支而非 main；`/team-ship` 需要感知当前是否在 release 分支上，自动选择 PR target
3. **`release → main` backport** — 发版后 hotfix + CHANGELOG 合回 main
4. **Release 分支清理** — 发版后删除 release 分支
5. **Release 分支保护** — `release/{version}` 也需要 branch protection（同 main 规则），防止直推

### B. Deploy Workflow

6. **`deploy.yml`** — `workflow_dispatch` 触发，参数 `env: [dev, staging, prod]` + `ref`
7. **Staging gate 对接** — `/team-release` 的 staging_workflow 指向真实 workflow
8. **可选：dev 自动部署** — push to main 后自动部署到 dev 环境

### C. Issue 版本追踪

9. **Found-in version label** — `/team-issue` 创建 bug 时自动加 `found-in:{version}` label
10. **Version labels 自动创建** — `/team init` 和 `/team-release` 在创建 milestone 时同步创建 `version:{version}` label
11. **Issue template 版本字段** — bug report template 增加 "发现版本" 字段
12. **Release 时 bug 回溯** — `/team-release` 增加 "found-in:{version} 但未关闭的 bug" 检查

### D. Skill 适配（受 release 分支影响的现有 skill）

13. **`/team-ship` 适配** — PR target 动态选择：在 release 分支上时 target release 而非 main
14. **`/team-claim` 适配** — hotfix 分支从 release 分支创建而非 main
15. **CI workflow 适配** — ci.yml 的 trigger branches 需要包含 `release/*`
16. **Branch protection 动态生成** — ✅ 已修复（本 session）

### E. Config Schema 改造

17. **`release_branch` 从静态值改为模式** — 现在 `conventions.release_branch` 是固定值（如 `main`），但实际需要 per-version 分支（`release/V0.1`、`release/V0.2`）。需要改为 pattern 或由 `/team-release prep` 动态管理

### F. team.md init 增强

18. **deploy.yml 模板生成** — `/team init` 时创建 deploy workflow 模板

## 技术决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| Branch protection | require PR + review=0 | 堵直推风险 + 保证 post-merge workflow 触发 |
| CI 不强制 | `required_status_checks: null` | CI 还不稳定 |
| Release 分支策略 | Git-flow-lite | main 持续开发，release 分支隔离验证 |
| Deploy 触发方式 | `workflow_dispatch` | Session R 共识：tag 是语义标记，不是部署触发器 |
| Found-in version | Label 方式 | GitHub 无原生字段，label 可过滤可统计 |
