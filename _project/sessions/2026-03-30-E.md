# Session Log — 2026-03-30 E

## Summary

- Added a decision-first foreground-admission rule to the scheduler.
- Proved that unresolved governed human decisions can now block new low-urgency foreground work when no established foreground batch is being continued.
- Preserved the existing sticky-foreground and parallel-capacity behavior by restoring the baseline smoke chain after the new hold scenario.

## Why

`Harness` already knew how to rank human decisions and defer lower-priority governed decisions behind the primary packet, but it could still admit fresh unrelated foreground work too eagerly. That left the control plane too willing to expand execution while the real bottleneck was still an unresolved leader/council decision.

## What Changed

- `harness/policies/defaults.yml`
  - added `execution.require_primary_human_decision_before_new_foreground: true`
- `internal/harness/runtime.go`
  - added scheduler admission rule `hold_for_primary_human_decision`
  - when a primary governed decision is unresolved and the scheduler is not merely continuing an already-established foreground batch, low-urgency runnable work is held back instead of admitted
  - urgent work still bypasses this rule through existing P0 / high-risk / release-adjacent logic
- `scripts/harness-smoke-test.sh`
  - added decision-hold scenario that pauses the old foreground, proves a fresh peer mission is withheld behind the outstanding decision backlog, then restores the foreground after backlog cleanup
- durable docs updated:
