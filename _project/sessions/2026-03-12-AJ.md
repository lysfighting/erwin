### Dashboard 超链接

用户报告 `/team` dashboard 的 issue number 没有超链接。排查发现两个原因：

1. **示例矛盾**：第 2378 行 priority_dot shorthand 的示例 `🟠 #134 Unified NanoClaw` 没有 bold，但第 2396 行规则要求 `**#NNN**`。LLM 照示例输出，自然无 bold → 无超链接。修复：示例改为 `🟠 **#134**`。
2. **{Pn} 冗余**：模板里 `{priority_dot} {Pn}` 同时出现，LLM 输出 `🟠 P1 #222`（dot + 文字标签）。而 priority_dot 的定义是"替代 Pn"。修复：全文删除 `{Pn}`（6 处）。
3. **规则加强**：第 2396 行改为明确 `ALWAYS **#NNN** (bold + zero-pad)`，补充"无 bold = 无超链接"。

### Dashboard assigned vs claimed

用户指出 `My Missions` 里有的 issue 显示 🟢 WIP 但实际没有 claim（无 worktree）。根因：模板只有 🟢 *wip* 一种状态，不区分 claimed 和 merely assigned。

修复：新增 ⚪ *assigned* 状态——issue assigned 但无 Contract/branch 时显示 ⚪，有 Contract + branch 时显示 🟢。同步改了 Leader Dashboard 和 Member Dashboard 两处模板。

### Worktree init bug

用户报告 `/team` 偶尔触发 init 流程（问 team size）而不是显示 dashboard。"不是必现的"——关键线索。

排查：`_detect_dir()` 用相对路径 `.teamwork/config.yml` 检测 config。在 worktree 中执行时，cwd 是 worktree 路径（如 `.claude/worktrees/refactor/`），`.teamwork/` 不在那里——它在主仓库里。

初次修复用了 `git rev-parse --show-toplevel`，但发现这在 worktree 里返回的是 worktree 路径而非主仓库。最终用 `git rev-parse --git-common-dir` 定位主仓库的 `.git` → 上一级就是主仓库根目录。

同步更新 e2e 测试断言（现在返回绝对路径）。

## Part 2: Cross-MC 知识共享设计

### 问题定义

4 个功能提案，本质是一件事：Mission 之间的信息隔离。

1. Issue 图片上传 → skip（GitHub CLI 限制，用户自行在 UI 上传）
2. 向其他 issue 共享知识 → L2: 主动推送
3. 接收其他 issue 的知识 → L1: 被动读取
4. 多轮讨论 → 共享的决策机制

### Claude Code Teams 调研

研究了 Claude Code 内置 team 通信机制：
- 文件邮箱 `~/.claude/teams/{name}/inboxes/{agent}.json`
- 消息格式 `{from, text, summary, timestamp}`
- **支持 peer-to-peer**：teammate 可直接 SendMessage 给另一个 teammate
- autoWake：消息到达时自动唤醒 idle agent
- 纯 JSON 文件 + 轮询，无 broker

### 类比与方案

GitHub issue comments 就是 cross-MC 的"文件邮箱"：

| Claude Code Teams | Cross-MC via GitHub |
|---|---|
| `inboxes/agent.json` | Issue #N comments |
| `SendMessage` | `gh issue comment` |
| `autoWake` | `/team-drive` 启动时读 comments |
| `config.json` members | `.teamwork/active/MISSION-*.md` |

### 瘟疫式传播防护

核心风险：错误知识通过 cross-MC 传播，层层叠加，无法追溯。

最小安全机制：
1. **人类网关**：推送前必须 AskUserQuestion 确认
2. **禁止转发**：只能分享第一手发现，不转发别人的知识
3. **来源追溯**：结构化 comment 格式，含 confidence 字段

### 命令设计

不新增独立 skill（保持 6 skill 限制），作为 `/team` 子命令：
- `/team sync` — rebase from base branch（从 team-ship 提升为独立入口）
- `/team share [#N]` — cross-MC 知识推送

分工：
- L1（读 comments）→ 改 `team-drive.md` Phase 0（自动）
- L2（推送知识）→ 改 `team.md` 新增 `/team share`（用户主动）
- sync → 改 `team.md` 新增 `/team sync`

## Part 3: Implementation (v3.8.5)

### `/team sync`（team.md Operation Sync）

从 team-ship.md 的 sync 逻辑提取，作为独立 `/team sync` 入口。步骤：SY1 → SY2 → SY2b（AI conflict resolution）→ SY3（summary + push）。`/team-ship sync` 继续保留（向后兼容）。

### `/team share [#N]`（team.md Operation Share）

5 步流程：SH1（prerequisites）→ SH2（determine target，支持指定 #N 或自动扫描重叠）→ SH3（compose structured comment）→ SH4（human gateway，AskUserQuestion 确认）→ SH5（post + confirm）。

结构化 comment 格式：`🔗 **Cross-MC** from **#{N}** (advisory)` + Context + Finding + Files + Confidence。

Anti-plague 规则写入 Operation Share 尾部，作为所有 teamwork skill 的共享约束。

### L1: Cross-MC Knowledge Intake（team-drive.md Step 0b2）

在 Step 0b（Issue Freshness）和 Step 0c（Worktree Guard）之间新增 Step 0b2。

`/team-drive` 启动时：
1. `gh issue view {issue} --json comments` 读取所有 comments
2. 过滤 `🔗 **Cross-MC**` 前缀
3. 显示给用户作为 advisory context
4. 注入 Contract AI Notes 的 `## Cross-MC Advisory` section

规则：advisory only、no transitive propagation、contradictions flagged but not auto-resolved。
