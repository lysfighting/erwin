## 1. 话题 1：自动循环上下文管理 — 完整分析

### 1.1 问题空间

```
当前状态：
  /self-drive → 单 agent loop → 每轮调用 /drive → /drive 内建 /clear 机制
  /team-*     → 手动 pipeline → 无 loop → 无自动迭代

目标状态：
  "需求自动领取交付"闭环 + loop = AI 自动迭代项目
  只需创建好 milestone + issues，AI 自动 claim → drive → ship → next

核心矛盾：
  Loop = 多轮迭代 → leader 上下文持续积累
  /clear = 上下文归零 → 但也丢失 loop 控制逻辑
  Agent team = teammate 干净 → 但 leader 不干净
```

三个子问题：
- A: Leader context 积累 — 谁来当 loop controller？它的上下文怎么办？
- B: 中断恢复 — loop 被打断后，怎么知道从哪继续？
- C: 多 agent session 的 loop 架构 — self-drive vs team vs 外部编排

### 1.2 四种架构方案（Claude 分析）

**方案 1: Leader-as-Loop（当前 self-drive 模式）**
```
Leader (一个 Claude session):
  while (issues remain) {
    claim → spawn team → drive → ship → team shutdown → next
  }
```
- 问题：leader 上下文线性增长，N 轮后 compaction 丢细节
- 优点：最简单，AI 可以跨轮学习

**方案 2: Per-Round /clear（drive 的 Context Handoff 模式）**
```
每轮：leader 读 GitHub → claim → 写 contract+plan → /clear →
      用户粘贴 bootstrap → drive → ship → 回到开头
```
- 问题：每轮需要用户粘贴 bootstrap，不 auto
- 优点：每轮上下文 100% 干净

**方案 3: 外部编排器（bash/Action 触发独立 Claude 调用）**
```
外部 loop (bash/cron):
  while issues=$(gh issue list ...); do
    claude-code "/team-claim && ..."    ← 每轮独立进程
  done
```
- 问题：Claude 失去"决定下一步做什么"的能力
- 优点：零上下文积累，最可靠

**方案 4: Leader-Light + Delegate-Heavy（混合）** ← Claude 推荐
```
Leader (轻量 loop controller):
  while (issues remain) {
    issue = pick_next()               ← leader 只做调度
    spawn round-agent(issue)          ← 全部工作委托
    wait for completion
    update state                      ← leader 上下文只有调度记录
  }
```
- 问题：leader 仍有积累，但量小得多（只有调度日志）
- 优点：AI 保持决策能力 + 上下文增长慢

### 1.3 方案 4 细化分析

**Leader 每轮的 context 增量估算**：

| 操作 | Context 增量 | 备注 |
|------|-------------|------|
| pick issue | ~500 tokens | 读 issue list + 决策理由 |
| spawn round-agent | ~200 tokens | 一个 Agent tool call |
| wait + verify | ~300 tokens | 收 agent 结果 + gh pr view |
| **每轮合计** | **~1K tokens** | 10 轮 ≈ 10K，可控 |

对比方案 1：leader 自己做 claim+drive+ship，每轮 50K-100K tokens。

**中断恢复设计**（基于 GitHub 即状态）：
```
中断前 GitHub 状态:
  Issue #12: closed (PR #15 merged)     ← 已完成
  Issue #18: open, label: status:wip    ← 可能有未完成 PR
  Issue #22: open, no assignee          ← 未开始

新 session 的 leader 读 GitHub:
  → #12 closed → skip
  → #18 有 wip label → 检查是否有 open PR → 有 → 从 ship 继续
  → #22 → 正常 pick
```

关键洞察：GitHub 的 issue 状态 + label + PR 关联已经是完整的 loop 状态机。不需要额外 loop-state 文件。

**Re-Anchor 机制**（每 3 轮）：
```
gh issue list --milestone "V0.1" --json number,state,assignees,labels
gh pr list --state open --json number,headRefName,statusCheckRollup
→ 重建完整项目状态视图 → 覆盖 context 中任何 stale 信息
```

### 1.4 Claude 自我挑战：round-agent 的能力边界问题

```
⚡ REBUTTAL against own proposal:
  round-agent 执行完整 claim→drive→ship，
  但 Agent teammate 无法调用 Skill tool（只有 Bash/Read/Write 等基础工具）
  → round-agent 需要直接执行 skill 的底层逻辑（gh 命令），
    而不是调用 /team-claim 等 skill
```

两条解决路径：
- **路径 A — Prompt 注入**：agent prompt 内联关键步骤。可行但 prompt 巨大，skill 更新时不同步。
- **路径 B — 脚本化核心操作**：抽成 bash scripts，agent 调用。更稳定，但前期投入大。
- **Claude 推荐混合**：claim+ship 是固定流程适合脚本化，drive 是创造性工作适合 prompt。

**Claude 分析**：

结论是压缩后的产物，压缩必然丢信息。如果推理链有个小偏差被压进结论里，下次 session 只看结论就会继承这个偏差——无从发现，因为推理过程丢了。

保留过程 = 给下次 session 独立验证的机会。它可以看推理链，自己判断结论是否成立，而不是盲信。

**新共识**：Session log 应同时记录讨论过程（推理链、trade-off 分析、对话转折）和结论。下次 session 应独立判断过程和结论的有效性。

## 3. Develop 分支保护讨论（转折点）

### 用户质疑 main 分支设计

用户问：main 分支可以有未验证的代码吗？Session R 设计中 dev 环境部署的是 main HEAD，main 上可能有未经 staging/QA 验证的代码。

Claude 分析了两种思路：
- **思路 A — main = 开发基线（Session R 设计）**：feature → main → dev，main 有未验证代码
- **思路 B — main = 已验证代码**：feature → develop → dev → 验证后 develop → main → staging → prod

用户明确：「业内最佳实践肯定不会让 main 有未经验证的代码」。

**决策：采用思路 B，引入 develop 分支。**

### 对 Session R 共识的修订

| 原共识 | 修订 |
|--------|------|
| push to main → auto deploy dev | push to **develop** → auto deploy dev |
| PR merge to main | PR merge to **develop** |
| staging 从 main 某个 ref | develop → main 合并后，从 main HEAD 部署 |
| /team-release 在 main 上打 tag | **不变**，main 此时已是验证过的代码 |
| squash merge | **不变**，feature → develop 仍是 squash |

### Skill 改动影响

| Skill | 改什么 |
|-------|--------|
| /team-claim | 从 **develop** (base_branch) 切分支 |
| /team-ship | PR target 改为 **develop** (base_branch) |
| /team-drive | 安全检查：不在 base_branch 且不在 release_branch |
| /team-release | 新增：先 merge develop → main，再在 main 上打 tag |

### 通用设计原则

用户强调：「设计不要耦合任何项目的设计，是通用设计，只不过是通过 vi-agent 去实践！」

因此 v2.6 的设计：
- `conventions.base_branch` = PR 合并目标（默认 "main"，可设为 "develop"）
- `conventions.release_branch` = 打 tag 的分支（默认 = base_branch，即单分支模式）
- 当 base_branch ≠ release_branch → 双分支模式自动激活
- 向后兼容：不配 release_branch = 现有 v2.5 行为
