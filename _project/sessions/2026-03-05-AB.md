### 深度调研发现

**Vibe Kanban 的真相（从 GitHub Issues + HN 讨论提取）：**
- 4 agent 硬件上限（MacBook 实测），26GB 磁盘 2 天吃光
- Agent 之间**零通信** —— 不知道彼此在做什么，语义冲突无解
- 放弃了 GitHub Issues，自建 SQLite issue 库 —— 和「GitHub-first」完全相反
- 用户已经在 old UI vs new UI 之间撕裂，GUI 本身也是维护负担
- **无 release 管理、无 CI/CD** —— 止步于 PR 创建
- 用户最大的夸赞集中在 **inline diff review**，不是看板本身

**CCPM 的真相（从 GitHub Issues + HN 讨论提取）：**
- **已废弃**（2025.9 最后一次提交），7.5K star 但 Issues 一片混乱
- 30+ 个 slash commands —— 命令爆炸，O(2^C)
- State 双写（本地 .md + GitHub Issues），需要手动 sync
- Bash 代码嵌在 prompt 里让 LLM 解释执行 —— **这正是 teamwork v2.6.1 的 21 个 bug 的根源，我们已经用独立脚本解决了**
- Context 文件会**幻觉**（CONTEXT_ACCURACY.md 自己承认了）
- 无 PR 流程，无 release，直接 merge main

### 三个产品解决的是三个不同问题

| | Vibe Kanban | CCPM | Teamwork |
|---|---|---|---|
| **核心问题** | "如何同时跑多个 agent 并看到结果" | "如何把 PRD 自动拆成 AI 可执行的任务" | "AI 如何融入团队已有的 GitHub 工作流" |
| **用户角色** | 个人开发者当「agent 经理」 | 个人开发者当「PM」 | 团队成员当团队成员（角色不变） |
| **核心假设** | 并行 = 效率 | 文档驱动 = 质量 | GitHub 原生 = 最低摩擦 |

### 值得吸收的三件事

**1. 可视化：GitHub Projects 外包 + 终端增强（两层方案）**

- GitHub Projects 已经是 GitHub Issues 最好的看板 GUI —— 免费、零维护
- `/team init` 多加一步：`gh project create` + 把 issues 自动关联进去
- 终端内 `/team` board 做 ASCII 汇总（issue × status × branch × PR）
- **不建 GUI，不写前端代码**

| 可视化层次 | 痛点 | 解法 | 成本 |
|------|------|------|------|
| **项目全局** | "所有 issue 什么状态？" | GitHub Projects 看板 | 极低（1 条 gh 命令） |
| **执行过程** | "agent 们现在在干嘛？" | `/team` board 增强 ASCII 汇总 | 低（纯文本） |
| **Review 细节** | "agent 改了什么？" | `/team-review` 终端 diff + feedback | 中（新子命令） |

**2. Review 反馈加速：缩短 review → feedback 路径**

Vibe Kanban 用户最夸的能力是 inline diff review。teamwork 当前 review 路径：agent 改完 → 创建 PR → 人去 GitHub review → 写 comment → agent 再读 comment。中间 3 次上下文切换。

解法不是建 GUI。是在 `/team-ship` 流程里加一步：PR 创建后，自动呈现 diff 摘要，用户在终端直接给 feedback。

**3. 批量任务分解：/team-issue decompose 子命令**

CCPM 的 PRD 管线太重（30+ 命令），但核心 idea 有价值。做法：`/team-issue decompose "feature description"` → LLM 拆 3-5 个 issues → 用户确认 → 批量创建。不做 PRD → Epic 两层结构，直接 feature → issues。一层。

### 必须避开的四个陷阱

| 陷阱 | 为什么看起来诱人 | 为什么是坑 |
|------|----------------|-----------|
| **建 GUI** | Vibe Kanban 看起来很酷 | 改变产品品类（skill → application），维护成本 10x，且 GitHub Projects 免费提供看板 |
| **Agent 无关** | 支持 10+ agent 听起来开放 | 深度集成 Claude Code（drive/contract/agent team）是核心优势，通用化 = 稀释 |
| **自建 Issue 存储** | 本地状态更可控 | CCPM 的双写 sync 问题就是教训。GitHub IS the system 是 ADR-0010 的核心决策 |
| **命令爆炸** | 每个能力一个命令 | CCPM 30+ 命令已经让用户困惑。6 个 skill 是上限，扩展靠子命令 |

### 一句话总结

**从竞品学到的最重要的一课不是功能，而是定位清晰度：** Vibe Kanban 赢在「看得见 agent 在做什么」，但输在自建了一整套跟 GitHub 重叠的基础设施。CCPM 赢在「需求到代码全链路」，但输在过度设计 + LLM 质量不可控。

Teamwork 应该坚持的：**零基础设施、GitHub 原生、端到端**。需要改善的：**让 GitHub 已有的可视化能力被 teamwork 用起来**（Projects 看板）+ **终端内的态势感知**。

## 当前状态

**讨论结论**：
1. Teamwork 的定位 = 「AI 融入团队已有 GitHub 工作流」，不是 agent 编排，不是任务分解
2. 可视化方案 = GitHub Projects 外包全局看板 + 终端 ASCII 增强 + review 路径加速
3. 四个陷阱明确：不建 GUI、不做 agent 无关、不自建 issue 存储、不命令爆炸
4. 批量任务分解 (/team-issue decompose) 是 nice-to-have，低优先级
