### Agent 1: Comment R/W 机制设计

#### Part 1: Reading Comments — 5 个嵌入点

**`/team-issue #N`（查看）**
- API: 合并到已有 `gh issue view` 调用，加 `comments` 字段（+0 次 API）
- 过滤: 排除 BOT + lifecycle（`Claimed by` / `PR #` / `All code tasks` / `Cross-MC`）
- 显示: `💬 **COMMENTS** ({count} human)` + 每条 author + relative_time + 前 3 行
- 阻断: 否

**`/team-claim`（Contract 生成）**
- API: 同上，合并到 Step 3 的 `gh issue view`（+0 次 API）
- 注入 Contract: `## Issue Comments ({count} at claim time)` section
- 存储 `comment_count` 到 Contract frontmatter
- 阻断: 否（但 Standalone Test 要求 Contract 反映 comment 中的需求变更）

**`/team-drive` Step 0b（执行前检查）**
- API: `tw-contract.sh check-comments {issue} {stored_count}`（+1 次 API）
- 有新 comments 时全量读取并展示
- 判断逻辑（skill 层）: 包含方向变更关键词（"change"/"instead"/"blocker"）OR 来自 MEMBER/OWNER → AskUserQuestion 确认；否则 advisory 展示
- 阻断: 方向变更时是，信息性 comments 否

**`/team-ship` Step 2（pre-flight）**
- API: `check-comments`（+1 次）+ `gh pr view --json reviewDecision,reviews`（+1 次，仅 PR 存在时）
- PR 有 `CHANGES_REQUESTED` → 阻断，要求先处理 review
- Issue 新 comments → 同 team-drive 判断逻辑

**`/team sync`（rebase 后）**
- API: `check-comments`（+1 次轻量）
- 仅展示一行 summary: `💬 {N} new comment(s) on **#{issue}** since claim`
- 阻断: 否

#### Part 2: Writing Comments

**Ship Side-Effect（主动通知其他 Issue/PR）**:
- 检测 `SIDE_EFFECT_FILES` 与其他 open mission Issues 的 Context Files 重叠
- 草拟 `⚠️ **Side-Effect Notice** from **#{current}**` comment
- **Human gateway**: AskUserQuestion（"Post" / "Edit" / "Skip"）
- `/team auto` 模式下跳过（零交互）

**Auto-share**: **永远不自动**。手动 `/team share` + human gateway。
- 唯一例外: breaking change（接口签名变更）→ 强提示 `🔴 BREAKING CHANGE` 但仍不自动 post
- Drive 完成时: 在 summary 中 nudge `📡 Run /team share #{sibling}`

#### Part 3: Script 实现

`tw-contract.sh` 新增 3 个子命令:

```bash
check-comments {issue} {stored_count}
# → UNCHANGED / NEW:{delta} / NETWORK_ERROR
# 一次 gh issue view --json comments，Python 过滤 lifecycle/bot

read-comments {issue} --exclude-bot --exclude-lifecycle --since {timestamp}
# → JSON array of {author, authorAssociation, body, createdAt}
# Python 过滤: strip_emoji_prefix() 匹配 lifecycle 前缀

store-comment-count {contract_file} {count}
# → 更新 Contract frontmatter 的 comment_count 字段
# Python 解析 YAML frontmatter，插入/更新字段
```

### Agent 2: Sync 语义扩展设计

#### 核心原则

sync 是 READ 操作 — 展示信息，不转换状态。**永远不阻断**。

#### Rebase 后的 4 个数据源

1. **Issue comments**: 用 `claimed:` 时间戳做锚点（已存在于 Contract）
2. **PR review comments**: `gh pr list --head "$BRANCH" --json reviewDecision,reviews`
3. **Base branch commit log**: rebase 已吸收，展示 count 即可
4. **Contract freshness**: 复用已有 `tw-contract.sh check-freshness`

#### 输出格式（VE 标准）

```
**SYNC COMPLETE** ────────────────────────────
  Branch:   *{branch}*
  Rebased:  `{N}` commits from *{BASE_BRANCH}*

**INFO SYNC** ────────────────────────────────
  Issue:    **#042** — `3` new comment(s) since claim
            *@alice* (2h ago): "We also need to handle the edge case..."
            *@bob* (1h ago): "Agree with Alice, plus the API rate limit..."
  PR:       `changes requested` — `2` unresolved thread(s)
  Contract: `fresh`
────────────────────────────────────────────
```

**隐藏规则**: 无新信息时整个 INFO SYNC 块隐藏。>10 条 comments 截断到最近 5 条。

#### 交互决策树

| Case | 行为 |
|------|------|
| 新 Issue comments（信息性） | 展示 peek，继续 |
| 新 comments 含需求变更关键词 | `⚠️` 标记，继续（不阻断） |
| PR `CHANGES_REQUESTED` | `⚠️` 展示 reviewer + 第一行，继续 |
| Contract stale | `⚠️` 提示 run `/team-drive` review，继续 |
| Semantic conflicts | 不检测（需要领域理解，team-drive 的事） |

#### 模式: 单模式，无 flag

不要 `--full` / `--info`。KISS。truncation 自动处理大量 comments。

#### 实现

新 script 子命令 `tw-contract.sh info-sync`:
- 打包 3 个 `gh` 调用（comments + PR + freshness）
- 输出结构化结果: `COMMENTS:3\nPR:changes_requested:2\nCONTRACT:fresh`
- Skill `.md` 解释为 VE 格式输出

### Agent 3: Multi-MC v4 架构设计

#### Part 1: 可行性分析

**Claude Code Team 工具限制**:
- TeamCreate 在**同一 session** 内 spawn subagents — 共享 context window
- SendMessage 是**临时的** — session 结束即消失
- 实际 parallelism ceiling: **2-3 MC**（每个 MC 需 30-50K tokens context）
- TeamCreate 设计为 **intra-MC**（单任务内并行），非 **inter-MC**（多任务间并行）

**Worktree 已支持**:
- team-claim 已支持 worktree 模式（并行 Contract + 独立目录）
- `.mission` marker 标识 worktree 归属
- 文件冲突仍可能（两个 MC 改同一文件）

#### Part 2: 四种架构对比

| 维度 | A: Pure Team | B: Sequential+Awareness | C: Hybrid | D: Multi-Session |
|------|-------------|------------------------|-----------|-----------------|
| 冲突风险 | 高 | 极低 | 低 | 中 |
| 通信开销 | 极高 | 低 | 低-中 | 最小 |
| 失败恢复 | 差 | 优秀 | 好 | 优秀 |
| Token 成本 | ~Nx + overhead | ~Nx | ~Nx + planning | ~Nx (真并行) |
| 质量 | 下降 | 最高 | 高 | 最高 |
| 完成时间 | min(MC) | sum(MC) | ~sum(MC) | max(MC) |

**推荐**:
- **MVP**: Option C — parallel claim + sequential drive + optional parallel for independent MCs
- **终极**: Option D — 多终端多 session，coordinator 只做 setup

#### Part 3: 通信协议

**两层通信**:

Layer 1 — **静态**（claim 时）:
- Contract 中 `## Related MCs` section: 列出所有 sibling MC + objectives + overlapping files
- 由 `/team auto-all` coordinator 注入

Layer 2 — **动态**（执行中）:
- 已有 `/team share` + Step 0b2 Cross-MC 机制
- 扩展: ship 完成后自动 post 标准化 completion comment:
  ```
  🔗 **Cross-MC** from #042 — SHIPPED (PR #150)
  Modified: src/auth.py (lines 42-78), tests/test_auth.py
  Interface change: authenticate(user, token) → authenticate(user, token, scope)
  ```

#### Part 4: 调度策略

```
1. FETCH all assigned open Issues with mission label
2. For each: scan Context Files (Glob/Grep)
3. BUILD overlap matrix (Issue_i × Issue_j → shared files)
4. BUILD dependency graph (explicit "depends on #N" + implicit write-before-read)
5. TOPOLOGICAL SORT by dependency, then priority
6. APPLY rules:
   - P0: 永不并行
   - P1: 最多 2 并行（零文件重叠时）
   - P2/P3: 最多 3 并行（零文件重叠时）
   - Parallelism cap = 3
7. OUTPUT JSON execution plan:
   [{"batch":1, "issues":[42], "mode":"sequential"},
    {"batch":2, "issues":[45,47], "mode":"parallel"}]
```

#### Part 5: v3.10 必须为 v4.0 准备的基础设施

| # | 能力 | v3.10 交付 | v4.0 使用 |
|---|------|-----------|----------|
| 1 | Comment 读写 | ✓ 3 个 script 子命令 | 跨 MC 通信 |
| 2 | Contract cross-reference | `## Related MCs` section format | Coordinator 注入 |
| 3 | File overlap detection | `tw-scheduler.sh overlap-check` | 调度算法 |
| 4 | Batch claim | worktree 模式对 auto-all 强制 | 并行 claim |
| 5 | Completion signal | 标准化 Cross-MC shipped comment | sibling MC 感知 |
| 6 | Scheduler script | `tw-scheduler.sh plan` | JSON 执行计划 |

## ⚫ Phase 6: 性能 + 稳定性评估

#### 🔮 Claude

### 评估结果

**API 延迟（实测 lysfighting/erwin repo）**:

| 调用 | 耗时 |
|------|------|
| `gh issue view --json number,title,body` | 769ms |
| `gh issue view --json comments` | 1373ms |
| `gh issue view --json number,title,body,comments`（合并） | 1287ms |

**关键发现**: 合并 comments 到已有调用 = +0ms 净增。独立调用 ~1.3s。

**每命令新增延迟**:

| 命令 | 典型 | 最差（500 comments） |
|------|------|---------------------|
| `/team-issue #N` | +0ms | +0ms |
| `/team-claim` | +0ms | +0ms |
| `/team-drive` | +1.3s | +8s |
| `/team-ship` | +2.5s | +14s |
| `/team sync` | +2.5s | +14s |

**3 个安全改进**:
1. 合并 API 调用（claim/issue +0 次）
2. 用 timestamp 替代 count（避免 add+delete 竞态）
3. 大 Issue 优化: >100 comments 时先用 REST `gh api .../issues/N` 拿 count（~300ms），变化时才全量

**Python3**: 已是 de facto 依赖（10 处现有调用），startup 35ms。

**稳定性**: 所有新调用用 `|| true` 非致命模式。失败 = 跳过 comment sync，不阻断。

**结论: 生产就绪。**
