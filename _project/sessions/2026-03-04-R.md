## 2. 闭环的原子单位讨论

### Claude 提问：闭环是 per-issue 还是 per-milestone？

- **方案 A — per-issue 闭环**：每个 issue 独立走完 claim → drive → ship → merge → done
- **方案 B — per-milestone 闭环**：所有 issue 积攒 PR，统一 merge + release

**共识**：方案 A。当前 teamwork 设计隐含的就是 per-issue。缺的是 merge 后的自动化。

### Claude 提问：PR merge 自动化还是只自动化 merge 后的 cleanup？

**用户回答**：PR merge 自动化要做，删除分支也要做。但这两个操作无比重要，所以最好有 tag，哪怕删了分支也可恢复。

**用户追问**：如果考虑删除分支后用 tag 恢复，是不是每次 merge 时 squash commit 最好？这样目标分支上 tag 和 tag 之间只有一个 commit，可以用 cherry-pick 重新做。

### Claude 分析：Squash merge 后什么会丢失？

| 丢失的 | 是否能恢复 | 重要吗？ |
|--------|-----------|---------|
| 分支名 | PR 记录里有 | 不重要 |
| 分支上的逐个 commit 历史 | 丢了 | 看场景 |
| 最终合并的代码 | squash commit 里全在 | 最重要的在 |

**关键判断**：只需恢复"最终成果"而非"开发过程" → squash commit 本身就够，`git cherry-pick` 一个 commit 即可还原。GitHub PR 页面永久保留 diff 和所有 commit 历史（即使分支删了）。

### 决策：Release tag 够了，per-merge tag 是过度设计

理由：
1. squash commit 已含完整代码变更
2. GitHub PR 永久保留历史
3. per-merge tag 会制造大量 tag 噪音

**用户确认**：同意路径 2（semi-auto），CI 通过后人点 merge。

## 3. Changelog + Milestone 联动

### 发现 vi_agent 现状

- 无 CHANGELOG.md
- 无 GitHub Milestones（config 里 V0.1 但 GitHub 上为空）
- 30 个 `dev-YYYYMMDD-hash` tag（部署用）
- 无 release tag

### Changelog 两条路

**路径 A — GitHub Release IS the changelog**：`--generate-notes` 从 merged PR titles 自动生成，零维护。
**路径 B — 自动生成 CHANGELOG.md 到仓库**：代码仓库自包含，但多一步维护。

### 跨 session 对齐

用户展示了 vi_agent session 的讨论内容。那边建议 git-cliff 半自动。

**对比分析**：

| | erwin session (本 session) | vi_agent session |
|---|---|---|
| Changelog 方案 | `--generate-notes` 为主 + append CHANGELOG.md | git-cliff 从 commit 生成 |
| Tag 时机 | release-only | 同 |
| Milestone 集成 | 未深入 | 轻量：只改 /team-issue + dashboard |

**核心差异**：git-cliff vs `--generate-notes`。如果用 squash merge，输入源相同（squash commit ≈ PR title）。

**决策**：A + 轻量 B。不引入 git-cliff（零外部依赖）。`/team-release` 时取 release body append 到 CHANGELOG.md。

### 跨 Claude session 通信问题

用户问："怎么让两个 Claude Code 通信？"

**答案**：GitHub Issues + 文件系统。这就是 "GitHub IS the system" 原则的元应用。两个 Claude session 通过持久化的外部存储通信，不靠内存。

**状态持久化分类**：
- 持久化（GitHub）：Issue, PR, Milestone, Release + tag, CHANGELOG.md
- Ephemeral（session 内）：Contract, drive state.md, 循环轮次状态

**用户确认**：循环轮次不需要持久化。中断 = 当前轮次作废，新 session 从 GitHub 状态重启。

## 5. 环境策略 — 详细讨论

### 用户关键说明

- 实践项目始终是 `../vi_agent`
- 要详细聊透，不是粗略
- QA 周期短（AI 测试）

### 分支策略：模式 A vs 模式 B

**模式 A — Tag-only（main 短暂冻结）**：
- milestone done → code freeze → rc tag → staging QA → release tag → prod
- freeze 期间新功能不能 merge
- 适合 QA 周期短的团队

**模式 B — Release branch（main 不冻结）**：
- milestone done → 切 release/V0.1 分支 → QA 在 release branch
- main 继续接受 V0.2 PR
- 适合 QA 周期长的团队

**用户选择**：模式 A。理由：QA 都是 AI 测，周期短。

### Dev 去 tag 化

当前 30 个 `dev-*` tag 问题：tag 应该是有意义的版本标记，不是部署日志。

**决策**：dev 环境部署不再打 tag。push to main → Action 自动部署。部署记录靠 Actions run history。

### 三环境部署设计

| 环境 | 触发 | 内容 |
|------|------|------|
| dev | push to main | main HEAD |
| staging | workflow_dispatch | 指定 ref |
| prod | workflow_dispatch | 指定 ref（release tag） |

## 6. 风险分离 — 关键设计讨论

### 用户关键反馈（转折点）

Claude 提议 `/team-release rc` 和 `/team-release` 共用一个 skill 管 staging 和 prod。

**用户反驳**："如果一个 skill 就能部署 staging 和 prod，那很危险不是吗？你要举一反三。"

### Claude 全面审查（举一反三）

| 操作 | 风险等级 | 问题？ |
|------|---------|--------|
| /team-drive 写代码 | 中 | **应检查不在 main 上** |
| /team-release 打 tag | 高 | **不应同时管 staging 和 prod** |
| close milestone | 中 | **应后置于 prod deploy 成功** |

### 提炼的设计原则

> **风险等级不同的操作不能混在同一个触发路径上。**

### 职责分离决策

**Skill 只管 git 操作（tag、branch），Action 管部署。**

- `/team-release` 只做：milestone check → AI audit → 确认 → git tag → gh release → CHANGELOG → close milestone
- 它不知道也不关心部署到哪里
- 部署是 Action 根据触发条件自动执行

### Staging 部署：tag-triggered vs workflow_dispatch

| | Tag-triggered | workflow_dispatch |
|---|---|---|
| 触发 | `git tag V0.1-rc1 && push` | `gh workflow run deploy -f env=staging -f ref=xxx` |
| 误触发 | 打错 tag = 触发错环境 | 参数明确，不容易搞混 |
| 灵活性 | 固定 tag pattern | 参数化，可选环境、版本、任意组合 |
| 回滚 | 需要删 tag 重打 | 直接 re-run 指定旧版本 |

**用户选择**：workflow_dispatch。

### 最终部署架构

```
Dev:      push to main → Action 自动部署（或 workflow_dispatch）
Staging:  gh workflow run deploy -f env=staging -f ref={commit/tag}
Prod:     gh workflow run deploy -f env=prod -f ref=V0.1
```

**rc tag 不再需要。** tag 只保留语义用途（release tag）。

**Action run status 作为门禁**：`/team-release` 打 tag 前检查 staging deploy Action 是否 success。GitHub Actions 有完整的执行记录（run history, step logs, artifacts），可通过 `gh run list` API 查询。

## 7. /team-ship done 改为 GitHub Action

**决策**：PR merge 后的 cleanup（close issue, label done）从手动 `/team-ship done` 改为 Action 自动触发。

理由：
- 减少手动步骤
- merge 是人工门禁（已足够安全）
- Action 还可检查 milestone 进度，100% 时通知

## 最终闭环设计

### Per-issue 循环（自动领取交付）

```
/team-issue        → 创建 issue (挂 milestone)
/team-claim        → 领取 → branch + contract
/team-drive        → 开发 + 测试 + commit (安全检查: 不在 main)
/team-ship         → push + PR
[人 merge squash]  → GitHub auto: delete branch
Action             → auto: close issue, label done, check milestone %
```

### Per-milestone（版本发布）

```
milestone 100%     → Action 通知
workflow_dispatch  → deploy to staging (指定 ref)
AI QA on staging   → Action log 记录结果
/team-release      → 检查 staging Action success
                   → git tag V0.1 → push
                   → gh release --generate-notes → append CHANGELOG.md
                   → close milestone → next version
workflow_dispatch  → deploy to prod (指定 ref=V0.1)
```

### 自动化循环（未来）

```
上述 per-issue 循环 + loop（参考 self-drive）
只需创建好 milestone + issues，AI 自动迭代
每轮循环是新 context（中断 = 作废，从 GitHub 状态重启）
```

## 设计原则（讨论中提炼）

1. **风险等级不同的操作不能混在同一个触发路径上**
2. **Skill 管 git 操作，Action 管部署**（职责分离）
3. **Action run status 是门禁依据**（不需要额外存储）
4. **闭环优先，最佳实践其次**
5. **不加新 skill，扩展现有 skill 子命令**
6. **Tag 是版本语义标记，不是部署日志**
