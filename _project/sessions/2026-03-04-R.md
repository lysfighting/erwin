## 2. 闭环的原子单位讨论

### Claude 提问：闭环是 per-issue 还是 per-milestone？

- **方案 A — per-issue 闭环**：每个 issue 独立走完 claim → drive → ship → merge → done
- **方案 B — per-milestone 闭环**：所有 issue 积攒 PR，统一 merge + release

**共识**：方案 A。当前 teamwork 设计隐含的就是 per-issue。缺的是 merge 后的自动化。

### Claude 提问：PR merge 自动化还是只自动化 merge 后的 cleanup？

**用户回答**（原文）：
> pr merge 自动化,删除分支也是要做的,但是由于这两个操作都是无比重要的,所以最好是有 tag,哪怕删了分支,也是可恢复的对吗?另外就是如果考虑删除分支,后续用 tag 恢复,那是不是每次 merge 的时候 squash commit 最好,这样合并后的目标分支上tag 和 tag之间只有一个 commit,可以用 cherry pick 来重新做是不是?

**用户同时提醒**：实践项目始终是 `../vi_agent`（underscore，非 hyphen）。

### Claude 分析：Squash merge 后什么会丢失？

| 丢失的 | 是否能恢复 | 重要吗？ |
|--------|-----------|---------|
| 分支名 | PR 记录里有 | 不重要 |
| 分支上的逐个 commit 历史 | **丢了** | 看场景 |
| 最终合并的代码 | squash commit 里全在 | **最重要的在** |

**关键判断**：只需恢复"最终成果"而非"开发过程" → squash commit 本身就够，`git cherry-pick` 一个 commit 即可还原。GitHub PR 页面永久保留 diff 和所有 commit 历史（即使分支删了）。

### 决策：Release tag 够了，per-merge tag 是过度设计

理由：
1. squash commit 已含完整代码变更
2. GitHub PR 永久保留历史
3. per-merge tag 会制造大量 tag 噪音

Squash merge 后的 main 样貌：
```
main: [V1.0] → squash(#12) → squash(#15) → squash(#18) → [V1.1]
               "feat: 用户认证"  "fix: token刷新"  "feat: skill加载"
```

**自动化方案**：
- GitHub repo 设置 "Allow squash merging"（强制 squash）
- GitHub repo 设置 "Automatically delete head branches"（merge 后自动删分支）
- 两个都是一次配置永久生效

**用户确认**：同意路径 2（semi-auto），CI 通过后人点 merge。

**路径 A — GitHub Release IS the changelog**：

## 5. 环境策略 — 详细讨论

### 用户关键说明

### 分支策略：模式 A vs 模式 B

**模式 A — Tag-only（main 短暂冻结）**：
```
main ──●──●──●──●──[freeze]──bugfix──bugfix──● V0.1 tag ──●──●── ...
       │  │  │  │                                          │  │
      #12 #15 #18 #22                                    #30 #31
       (V0.1 features)          (QA期间只修bug)            (V0.2 开始)
```
- milestone done → code freeze → rc tag → staging QA → release tag → prod
- freeze 期间新功能不能 merge
- 适合 QA 周期短的团队

**模式 B — Release branch（main 不冻结）**：
```
main ──●──●──●──●──●──●──●──●──●── ...
       │  │  │  │  │  │  │  │  │
      #12 #15 #18 #22 │ #30 #31│
       (V0.1)         │  (V0.2) │
                      │         │
release/V0.1 ─────────┤         │
       │              │         │
      bugfix──bugfix──● V0.1 tag│
       (QA 在这里做)             │
                                │
release/V0.2 ───────────────────┘
```
- milestone done → 切 release branch → QA 在 release branch → main 继续 V0.2
- 适合 QA 周期长的团队

**对比表**：

| 因素 | 模式 A (tag-only) | 模式 B (release branch) |
|------|-------------------|------------------------|
| 复杂度 | 低 | 中 |
| 6 人团队 | 够用 | 有点重 |
| QA 周期短（1-3天） | 完美 | 过度设计 |
| QA 周期长（1-2周） | 阻塞开发 | 有必要 |
| 自动化难度 | 简单 | release branch 切/merge-back 要自动化 |

**用户选择**：模式 A。理由（原文）：QA 周期短，都是 AI 测。

### Dev 去 tag 化

当前 30 个 `dev-*` tag 的问题展示：
```
dev-20260302-59405c7
dev-20260302-7a6d2fe   ← 同一天两个，看不出区别
dev-20260303-0814e72
dev-20260303-14acda7
... (30 个)
```

**原则**：Tag 应该是有意义的版本标记，不是部署日志。

**替代方案**：
```
当前:  merge → dev skill → git tag dev-YYYYMMDD-hash → deploy
改为:  push to main → GitHub Action → deploy to dev (no tag)
```

部署记录靠 GitHub Actions run history。`git tag -l` 只有干净的 release tag。

**用户确认**：同意 dev 去 tag 化。

### 三环境部署设计（初版 — tag-triggered）

| 环境 | 触发条件 | 部署内容 | 谁触发 |
|------|---------|---------|--------|
| dev | push to main (merge PR) | main HEAD | 自动 (GitHub Action) |
| staging | `V0.1-rc*` tag pushed | tag 指向的 commit | 手动打 tag |
| prod | `V0.1` tag pushed | tag 指向的 commit | `/team-release` |

对应 GitHub Actions 骨架（初版）：
```yaml
# .github/workflows/deploy.yml
on:
  push:
    branches: [main]        # → deploy to dev
    tags:
      - '*-rc*'             # → deploy to staging
      - 'V*'                # → deploy to prod
      - '!*-rc*'            # 排除 rc tags 走 prod

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          if [[ "$GITHUB_REF" == refs/heads/main ]]; then
            ENV=dev
          elif [[ "$GITHUB_REF" == *-rc* ]]; then
            ENV=staging
          else
            ENV=prod
          fi
          # deploy to $ENV
```

| /team-ship push + PR | 低（PR 可关） | 独立 skill | OK |
| merge PR | 中（进 main） | 人点 | OK，人是门禁 |
| auto-close issue | 低（可 reopen） | Action | OK |
| deploy to dev | 低（内部） | Action on push to main | OK |
| deploy to staging | 中（验证环境） | ？ | **不应和 prod 同 skill** |
| deploy to prod | **高** | ？ | **必须最高门禁** |
| close milestone | 中（不可逆感强） | /team-release 内 | **应后置于 prod deploy 成功** |

**发现 3 个问题**：
1. `/team-release` 不应同时管 staging 和 prod
2. `/team-drive` 没有"不在 main/production 上"的安全检查
3. close milestone 应后置于 prod deploy 成功

### 提炼的核心设计原则

> **风险等级不同的操作不能混在同一个触发路径上。**

### 职责分离决策

**Skill 只管 git 操作（tag、branch），Action 管部署。**

- `/team-release` 只做：milestone check → AI audit → 确认 → git tag → gh release → CHANGELOG → close milestone
- 它**不知道也不关心**部署到哪里
- 部署是 Action 根据触发条件自动执行

### 最终架构图

```
Skill 层 (Claude 执行):           Action 层 (GitHub 执行):
  /team-issue → issue               on push main → deploy dev
  /team-claim → branch              on workflow_dispatch → deploy staging/prod
  /team-drive → code
  /team-ship  → PR                  每次 run 都有 log + status
  /team-release → tag
    ↑ 打 tag 前检查                  ↑ 提供检查依据
    Action staging run = success?
```

### Staging 部署：tag-triggered vs workflow_dispatch

| | Tag-triggered | workflow_dispatch |
|---|---|---|
| 触发方式 | `git tag V0.1-rc1 && git push` | `gh workflow run deploy -f env=staging -f version=V0.1-rc1` |
| 可见性 | tag 永久留在 git history | Action run history（也永久） |
| 灵活性 | tag pattern 决定环境，固定 | 参数化，可选环境、版本、任意组合 |
| 误触发 | 打错 tag = 触发错环境 | 参数明确选择，不容易搞混 |
| 回滚 | 需要删 tag 重打 | 直接 re-run 指定旧版本 |
| 适合 | "tag 即发布"的仪式感 | 运维操作，需要灵活控制 |

**用户选择**：workflow_dispatch。

**workflow_dispatch YAML 骨架**（最终版）：
```yaml
# .github/workflows/deploy.yml
on:
  workflow_dispatch:
    inputs:
      env:
        type: choice
        options: [dev, staging, prod]
        required: true
      ref:
        description: 'Git ref to deploy (branch, tag, or SHA)'
        required: true
        default: 'main'
```

部署流程：
```
Dev:      自动（push to main 触发）或 gh workflow run deploy -f env=dev -f ref=main
Staging:  gh workflow run deploy -f env=staging -f ref=V0.1-rc1
Prod:     gh workflow run deploy -f env=prod -f ref=V0.1
```

**结论**：rc tag 不再需要。tag 只保留语义用途（release tag）。deploy 全靠 workflow_dispatch。Tag 和 deploy 完全解耦。

### GitHub Actions 执行记录能力

用户确认 Actions 有日志后，确定用 Action run status 作为门禁：
- **Run history**：每次触发的列表，含状态（success/failure/cancelled）
- **Step logs**：每个 step 的详细输出
- **Artifacts**：可上传测试报告、截图等
- **API 可查**：`gh run list --workflow deploy.yml` / `gh run view {run-id} --log`

`/team-release` 打 tag 前可以检查：
```bash
gh run list --workflow deploy.yml --branch main --limit 5 \
  --json conclusion,headBranch,event,displayTitle
```

## 设计原则（讨论中提炼）

1. **风险等级不同的操作不能混在同一个触发路径上**（staging ≠ prod）
2. **Skill 管 git 操作，Action 管部署**（职责分离）
3. **Action run status 是门禁依据**（不需要额外存储 QA 结果）
4. **闭环优先，最佳实践其次**（用户明确优先级）
5. **不加新 skill，扩展现有 skill 子命令**（6 个是上限）
6. **Tag 是版本语义标记，不是部署日志**
