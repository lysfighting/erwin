## 1. Teamwork 视觉设计统一（emoji visual encoding）

### 背景

用户指出 `/team` dashboard 输出问题：
- 纯靠缩进，无视觉层次
- 标题没有高亮或辨识度
- 多个 skill 页面设计语言不统一
- 冗余信息多（空状态占位太啰嗦）
- 耗时 1m24s 太慢（7-8 个串行 API 调用）

### 设计方案

由于 Claude Code 文本输出走 markdown 渲染，**无法使用 ANSI 颜色**。但 Bash 脚本的 stdout 可以正常渲染 ANSI escape codes（用户注意到 install.sh 有颜色输出并提问确认了这一点）。

最终方案：emoji + Unicode 符号增强视觉。

### Visual Encoding Rules（定义在 team.md，全局适用）

| Symbol | Meaning | Used for |
|--------|---------|----------|
| 🔴 | P0 (critical) | priority dot |
| 🟠 | P1 (high) | priority dot |
| 🟡 | P2 (medium) | priority dot |
| ⚪ | P3 (low) / idle | priority dot / member status |
| 🟢 | Active / WIP | member status |
| ⚡ | Issue updated since claim | stale marker |
| ✅ | CI pass / task done | CI icon / completion |
| ❌ | CI fail | CI icon |
| ⏳ | CI pending | CI icon |
| 🎯 | Objective / Mission | section icon |
| 📋 | Sub-tasks / list | section icon |
| 📁 | Context files | section icon |
| 🔀 | Branch / PR | section icon |
| 📦 | Created / Shipped | section icon |
| 🏁 | Complete / Milestone | section icon |
| 💬 | Comment | section icon |
| ✏️ | Update / Edit | section icon |
| 📊 | Stats / Assessment | section icon |
| 🏷️ | Labels / Tag | section icon |
| 🔍 | Adopt / Search | section icon |
| 🚀 | Launch / RC / Promote | section icon |
| ⚠️ | Warning / Untracked | section icon |
| 👥 | Team members | section icon |

Progress bar: `█` filled + `░` empty, 10 chars. E.g., 14% → `█░░░░░░░░░`

### 应用范围

6 个 skill 文件的所有输出模板全部更新：

- **team.md** — Leader/Member dashboard, Queue, MC Detail
- **team-claim.md** — CLAIMED briefing, assigned missions list
- **team-issue.md** — PREVIEW, CREATED, MC Detail, COMMENT, CURRENT, UPDATE, ADOPT, MILESTONE (11 templates)
- **team-drive.md** — MISSION briefing, PLAN ASSESSMENT, TOPOLOGY, WAVE MAP, broadcasts, COMPLETE
- **team-ship.md** — SHIPPED, DONE
- **team-rc.md** — RC PREPARED, PROMOTE, PROMOTED, existing RC warning

### Dashboard 性能优化

7-8 个串行 `gh` API 调用改为 4-5 个并行调用。关键变化：一次 `gh issue list --label mission` 获取全部 mission issues，客户端按 label 内容过滤（wip/review/done），替代 3 个独立调用。

## 3. 闭环设计讨论

### 话题 A：`/team-wrap` — 反向闭环（代码已改好，补全 teamwork 流程）

**场景**：用户直接让 AI 改代码，改完后想补 issue/PR 走正规流程。

**三条路径**（按改动状态）：

| 状态 | 策略 |
|------|------|
| 未 commit | stash → issue → claim（切 branch）→ apply stash → drive → ship |
| 已 commit 未 push | issue → claim（切 branch）→ cherry-pick → base reset to origin → drive → ship |
| 已 commit 已 push | 只能追认（issue + labels + close），无法走 PR 流程 |

用户确认：**不跳过 claim 和 drive**。即使是事后补，也要保证环境干净（mission branch 从 clean base 切出）。已 commit 未 push 时可以 cherry-pick 到 mission branch，然后 base branch reset 回 origin 版本。

**设计状态**：路径清晰，可以直接实现。

### 话题 B：正向闭环自动化 — `issue → claim → drive → ship → done → next`

**当前状态**：6 步全手动触发，步与步之间无自动衔接。

```
/team-issue → /team-claim → /team-drive → /team-ship → [人 merge] → /team-ship done
   手动         手动          手动           手动         手动           手动
```

**Session R 历史讨论**（2026-03-04）：
- 讨论了「需求自动领取交付」完整闭环
- 确定 per-issue 闭环（方案 A），不是 per-milestone
- 设计了完整流程图：issue → claim → drive → ship → [人 merge] → auto deploy dev → milestone 满 → /team-rc → staging → /team-rc promote → prod
- 讨论了上下文爆炸问题：每次循环结束应该是新上下文，leader 不断积累 context 是问题
- 讨论了中断恢复：Contract 持久化 checkbox 进度，可以从断点恢复
- **未落地**：纯设计讨论，无代码产出

**本次讨论新增洞察**：

正向闭环的切入点有两个方向：
1. **串联命令**（如 `/team-auto`）：一个命令跑完 claim → drive → ship
2. **尾部衔接**：每个 skill 结束时自动引导下一步（如 `/team-ship done` 结束后展示 queue + 提示 claim）

最简单的闭环可能不是 loop，而是把 6 步的断点从「人记住流程」变成「系统引导下一步」。

**设计状态**：延后实现，先做好 `/team-wrap`（话题 A）。
