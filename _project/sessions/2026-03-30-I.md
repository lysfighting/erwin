# Session Log — 2026-03-30 I

## Summary

- Added sticky bounded parallel-batch retention to the scheduler.
- Proved that a fresher same-class peer no longer churns an already-admitted parallel batch.
- Kept bounded-capacity pressure visible by preserving explicit defer actions for overflow peers even when the batch is retained.

## Why

`Harness` already retained sticky foreground missions and sticky primary human decisions, but bounded parallel batches could still thrash when a fresher same-class peer appeared. That made portfolio scheduling less stable than the rest of the control plane and pushed the system toward freshness churn instead of deliberate admission continuity.

## What Changed

- `internal/harness/runtime.go`
  - added sticky parallel-batch selection based on the previous admitted mission set
  - scheduler now reuses an otherwise-valid bounded parallel batch before admitting a fresher same-class peer
  - snapshots now expose `previous_selected_mission_ids`
  - overflow peers still become explicit `defer_due_parallel_capacity` actions even when the admitted batch is retained
- `scripts/harness-smoke-test.sh`
  - added a fresher same-class peer on top of an existing bounded parallel batch
  - verified `selection_policy: sticky_parallel_batch`
  - verified `previous_selected_mission_ids`
  - verified capacity deferral remains visible for the fresher peer
- durable docs updated:

## Validation

## Result

The scheduler now behaves more like a real portfolio controller. It can keep a bounded parallel batch stable across same-class churn while still surfacing overflow pressure explicitly, instead of recomputing the admitted set from freshness alone every pass.
