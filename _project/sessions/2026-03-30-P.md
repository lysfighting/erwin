# Session Log — 2026-03-30 P

## Summary

Turned bundle-scoped active councils into first-class scheduler state instead of leaving them visible only inside individual decision packets.

## What Changed

- Extended meeting activity projection so runtime now tracks active meetings by `bundle_id` as well as by `source_decision_id`.
- Scheduler mission classifications now project:
  - `bundle_active_decision_meeting_ids`
  - `bundle_active_decision_meeting_count`
  - `bundle_control_state`
- Once a bundle-scoped decision has already been materialized into a live meeting, scheduler now:
  - upgrades affected missions to explicit bundle `active-council` awareness
  - counts `active_council_bundle_count` at portfolio level
  - emits `hold_for_active_bundle_council` for ready/executing peers that should stay behind the live bundle council
- `home` now mirrors `scheduler_active_council_bundle_count` and bundle-council runtime state so leader surfaces stay aligned with scheduler truth.
- Core smoke now proves:
  - a bundle-scoped scheduler decision can be materialized into a council
  - scheduler counts that bundle as an active-council bundle
  - mission classifications inherit bundle-level active council coverage
  - scheduler emits `hold_for_active_bundle_council`

## Result

`Harness` now treats a live bundle council as active portfolio governance, not just a materialized meeting plus generic overlap metadata. That closes another control-plane gap between broader bundle adjudication and automated council execution.
