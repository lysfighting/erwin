## 对话过程：从使用说明到举一反三审计

### 话题 1：Teamwork 使用流程

用户问 "这套 teamwork skill 该如何使用呢?"

这个问题的价值不在于答案本身（流程是固定的），而在于它暴露了一个认知差距：
skill 设计者（我）清楚 Issue→Claim→Drive→Ship→Release 的完整链路，但用户需要的是一个 quick-start 视角。
回答中总结了核心循环 + 辅助命令表 + 一句话概括。

### 话题 2：Auto-merge 和 branch 删除

用户问 "之前提到的自动 merge 和 delete branch 怎么做来着?咱们讨论出结果了吗"

搜索 Session R 记录后确认：
- **PR merge = 人工点按钮**（没有完全可信测试套件前不自动 merge）
- **Branch 删除 = GitHub 仓库设置** `Automatically delete head branches`
- **Squash merge = GitHub 仓库设置** 只开 `Allow squash merging`
- **Per-merge tag = 不需要**（squash commit + PR 历史足够可恢复）

这些结论在 Session R 已经达成共识，但当时停留在"去 GitHub Settings 手动操作"层面。

### 话题 3：关键转折 —— "这些流程是 team 能够实现的吗?"

**这是本次对话最有价值的一个问题。**

用户没有问"怎么手动配置这些设置"，而是问"team skill 能不能搞定这个"。
这个问题把视角从"我们讨论了什么"拉到"我们的工具做到了吗"。

答案是：**没有。** `/team init` 的 Step 5 只有 labels 和 branch protection，auto-delete 和 squash merge 完全缺失。
Session R 的设计决策没有 100% 落地到 skill 实现中 —— 这是一个 知行不合一 的 gap。

我提出可以通过两行 `gh api` 调用解决：
```bash
gh api repos/{REPO} --method PATCH --field delete_branch_on_merge=true
gh api repos/{REPO} --method PATCH --field allow_squash_merge=true ...
```

### 话题 4：举一反三审计 —— "肯定还漏掉别的了"

用户不满足于只补两个 API call，要求系统性排查。这体现了用户一贯的原则：
**发现一个漏洞时，不应该只修一个，要审计所有同类操作。**（Session R 已建立的共识）

系统审计 `/team init` Step 5 后找到 **5 个 gap**（不是 2 个）：

1. **Auto-delete head branches** — merge 后分支堆积
2. **Squash merge only** — 混乱的 merge commit 历史
3. **Squash commit message format** — `PR_BODY` 保证 `Closes #N` 自动关 Issue
4. **Release branch 无保护** — 双分支模式下 main 裸奔
5. **CI 模板写死 `[main]`** — 双分支模式下 CI 不触发

前 2 个是用户原始问题的直接延伸。
第 3 个是从 squash merge 举一反三 → commit message format 影响 Issue 自动关闭。
第 4 个是从 branch protection 举一反三 → 只保护 base_branch，release_branch 完全没保护。
第 5 个是从 branch 配置举一反三 → CI 触发条件也用了硬编码 `main`。

### 方法论收获

这次对话链条：**使用说明 → 历史决策回顾 → "工具做到了吗?" → 发现 gap → 举一反三扩大到 5 个 gap**

核心模式：每次做完一个改动，应该问 "同类操作还有哪些？" 而不是 "这一个改了就行了"。
Session R 的共识 #N（举一反三）在这里得到了实践验证。

## 话题 5：Issue #70 审查 → post-merge Action

### 触发：vi_agent Issue #70 执行 gap

用户要求审阅 vi_agent Issue #70。发现：
- PR 已 merge，但 Issue 所有 checkbox 仍为 unchecked
- Label 停留在 `status:wip`，未更新为 `status:done`
- GitHub 的 `Closes #N` 只改 state（open→closed），不改 labels 和 checkboxes

**根因**：没有 post-merge 自动化。`/team-ship done` 是手动触发的，容易被遗忘。

### 转折："post-merge Action 没实现?"

用户的关键问题：**"team 工具应该帮仓库创建这些吧?"**

这和话题 3（"这些流程是 team 能够实现的吗?"）是同一个思维模式：
用户不关心"谁负责做这件事"，关心的是"我的工具是否覆盖了这个场景"。

答案同样是：**没有。** `/team init` 生成了 ci.yml，但没有 post-merge.yml。

### 设计决策

- **post-merge.yml 由 `/team init` 生成**（和 ci.yml 同级），不是用户手动创建
- **`actions/github-script@v7`**：纯 JS GitHub API 操作，零外部依赖
- **全勾策略**：用户确认 "全勾可以的" — PR merge 意味着 Issue 完成，checkbox 全部勾选
- **Milestone 完成检测**：当最后一个 Issue 关闭时，自动评论提醒可以 `/team-release`
- **team-ship done 降级为 fallback**：D3/D4 先检查 Action 是否已处理，跳过已完成的操作
- **Label prefix 配置化**：post-merge Action 使用 `{STATUS_PREFIX}` 占位符，`/team init` 生成时替换

### Changes Made

- **team.md Step 4e**: 新增 post-merge.yml 生成（40+ 行 `actions/github-script@v7`）
- **team.md Step 4f/4g**: hooks 和 gitignore 重编号（原 4e/4f）
- **team-ship.md D3/D4**: 从主动操作改为 fallback（先检查后操作）
- **Config health check**: 新增 post-merge Action 对 label_prefix 的依赖说明
