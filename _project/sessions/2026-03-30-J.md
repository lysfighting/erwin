# Session Log — 2026-03-30 J

## Summary

Promoted scheduler maintenance from unordered backlog into a first-class portfolio slice. `Harness` now exposes a primary maintenance action, deferred-maintenance count, and maintenance-selection metadata, and governance-critical maintenance can actively block low-urgency foreground admission through `hold_for_primary_maintenance`.

## Why

The control plane already knew how to surface stale runs, stale signals, stale meetings, and invalid explicit bundle governors as maintenance. The deeper remaining scheduler gap was that maintenance still behaved like a side list instead of a governed portfolio input. This left a mismatch between “the leader knows governance is broken” and “the scheduler still keeps opening fresh low-urgency foreground work.”

## What Changed

- Added scheduler maintenance ordering and stickiness helpers in the Go runtime.
- Exposed `primary_maintenance_action`, `deferred_maintenance_action_count`, `maintenance_selection_policy`, and `previous_primary_maintenance_key` in scheduler snapshots.
- Added runtime gating so critical governance maintenance can emit `hold_for_primary_maintenance`.
- Mirrored the new maintenance-first metadata into `home`.
- Added smoke coverage proving stale explicit bundle governance becomes primary maintenance and blocks low-urgency foreground admission until governance is cleared.
- Bumped adapter version to `0.67.0-prototype`.

## Result

`Harness` is now closer to a release-grade portfolio scheduler: human decisions and governance maintenance both behave like first-class control-plane backlog, instead of only mission execution being prioritized while governance cleanup remains advisory.
